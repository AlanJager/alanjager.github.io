在 RTX 3090 和 32GB 内存上试用 Strata

在一张 24GB 显卡和 32GB 系统内存上，Strata 能完成哪些任务，回答要等多久？本文用 RTX 3090 安装 Qwen3.8-Flash-Next 的 IQ2_XS 模型，依次测试中文多轮对话、SVG 生成和长输入。

中文四轮对话每轮用了约 17–46 秒，一幅完整的鹈鹕骑自行车 SVG 用了约 70 秒。长输入最初触发引擎退出，把 prefill 分块改为 256 后，约 4K 和 16K 输入都生成了设定的 64 个正文 token。后面继续看这些任务怎样执行，以及等待发生在哪里。

专家权重放在哪里，谁来计算？

Strata 是面向 Qwen3.8-Flash-Next 等模型的本地推理引擎，提供聊天界面和兼容常用客户端的 API。本轮使用 0.1.43。项目说明

MoE 模型通过路由器为每个 token 选择一部分专家。Strata 将常用专家的权重缓存到显存，GPU 直接执行这些专家；保存在 RAM 中的专家由 CPU 计算，或通过 PCIe 搬到 GPU 计算。CPU 和 GPU 的结果再合并，继续下一层。实现说明

以一个被路由器选中的专家为例，执行路径可以展开成三种：

显存缓存命中时，可以直接使用 GPU 上的权重。走 RAM 路径时，CPU 执行专家计算会使用 CPU 算力和内存带宽；GPU 读取 RAM 中的权重会使用 PCIe 链路和内存带宽。引擎合并各条路径上的计算结果，得到这一层的输出。

这一层缓存控制的是专家权重放在 RAM 还是显存。模型还会访问 GGUF 中的其他数据，其中一张 PLE / n-gram 表与本轮的磁盘等待有关，后面结合线程栈看这条路径。

多轮对话能否保留上下文和纠正数据？

为检查上下文和指令跟随，测试设置了一组假设的排障数据：首字要 240 秒，CPU 利用率 15%、GPU 利用率 10%，存在 D 状态线程和缺页。第一轮让模型给出排查方向，第二轮补充线程栈，第三轮把题目中的磁盘读速率从 80MB/s 纠正为 20MB/s，最后要求整理成 JSON。

每一轮都把前面的用户消息和实际助手回答一并传回，保持同一段对话。

轮次 任务 首字时间 全部完成
1 给出排障方向 15.97s 46.26s
2 补充缺页和线程栈 7.24s 26.91s
3 纠正 80 → 20MB/s 6.68s 17.38s
4 输出严格 JSON 9.72s 23.53s

四轮都完整结束。最后的 JSON 包含 facts、hypotheses、next_steps 三个字符串数组，保留了纠正后的 20MB/s、CPU / GPU 利用率和 D 状态栈。后续请求也报告了前缀 token 复用。

诊断回答中，模型将缺页现象解释为“内存严重不足”，并进一步推断随机小 I/O 延迟高；最后给出的动作是检查缺页、验证 I/O 延迟和排查线程同步。它给出了方向，但验证步骤比较笼统，实际排障时还要补上对应的采样工具和数据。

更早的一次 MoE 问答还给出了“全部专家必须放在 GPU 显存”的错误回答。Strata 的实际运行路径使用 RAM 和显存共同保存专家，这个问题的回答需要纠正。

长输入触发退出，缩小分块后怎样？

短任务跑通之后，运行项目的官方 benchmark。默认 prefill auto 下，这台机器实际使用的最大分块是 8192；约 4K 和 16K 输入各跑三次，六次都触发 watchdog 中止，引擎退出。watchdog 用来检查执行步骤是否长时间停滞，触发时记录诊断信息并中止引擎。

已有文本先经过 tokenizer 转成 token，随后进入 prefill：逐层处理输入 token，建立后续生成使用的上下文状态。分块大小控制一次处理多少个输入 token；--prefill 256 表示每块最多 256 个，约 4K 的输入会拆成多块依次处理，随后开始生成回答。

把配置 args 中的 --prefill 值改为 256，重启服务后再测，保留相同的模型、量化、上下文和单请求设置。

这轮复测沿用官方 benchmark 的合成输入方式：将 orbit、stone、river、needle 等 20 个英文词重复组成长词表，构造约 4K 和 16K token 的输入，末尾要求模型“用五句话概括词表里有哪些类型的词”。为了观察长输入处理后的首字时间和短段生成，设置 reasoning_effort: none、max_tokens: 64，结果如下。

输入规模 实际输入 token 正文输出 token 首字时间 请求结束 结束原因
约 4K，第一个样本 3939 64 252.73s 267.79s length
约 4K，后续重叠文本 3939 64 6.26s 15.20s length
约 16K，部分重叠语料 15716 64 225.87s 235.10s length

三个请求都处理完输入，开始生成词语分类的正文，并在输出第 64 个 token 后结束。响应均为 HTTP 200，流式连接收到结束标记，引擎在这三个样本中持续运行。

实际回答包含对自然、地质、物体等词语的分类。例如 16K 样本先提到 stone、quartz、canyon、river、meadow 等景观词，第三句写到 household or decorative items 时就停止了，五句话的要求尚未完成。记录中的思考内容为空，64 token 都是正文输出；length 表示正文达到本次设置的输出上限。

把 prefill 分块从 8192 改为 256 后，这三个样本都走完了“长输入处理 → 首字输出 → 生成 64 个正文 token”的运行过程。

分块变小后，日志中的驻留专家 RAM 从 18.79GiB 降到 15.28GiB，prefill 借用的 GPU 槽位也从 2812 降到 199。更小的输入块同时改变了这一阶段的内存占用和专家布局。

第二次约 4K 输入的文本主体与第一次大幅重叠，首字时间从 252.73 秒降到 6.26 秒。两次请求的 KV token 复用数都为 0，运行期间保留了系统页缓存和自适应专家策略。

线程停在文件页读取路径

模型的 PLE / n-gram 表按输入 token 和前面的 token 计算行号，再取出对应的向量参与后续计算。这张表约 28.8GB，本机通过 mmap 保留文件映射。访问某一行时，相应文件页若尚未驻留内存，读取会进入文件页加载路径。取行和读表实现

首字前的等待，时间线上能看到什么？

为了看清等待期间发生了什么，另开一轮带观测的运行：在固定源码上加入可选的主机观测，记录专家执行计划和缓存映射，再与 RAM、显存、CPU / GPU 利用率、磁盘吞吐和读等待对齐。

可以打开 专家与资源时间线，选择“约4K文本阅读”，拖动游标看专家分布和资源数值，也可以播放这段记录。这个页面自带数据，下载后能离线查看。

这段记录来自一次带观测的运行，依次执行中文解释、Python 修复和约 4K 输入三个请求，共采集 6720 个路由事件。

横向是采集开始后的时间，纵向是 48 个主模型层，每一列汇总一秒内的事件。蓝色表示选中专家的 GPU 缓存占比超过 70%，橙色表示占比在 70% 及以下；明暗表示选择次数。沿着同一层向右看，可以看到这层在不同时间窗口里的专家选择。右侧再展开该层，查看具体专家编号和缓存状态。

截图选中了“约4K文本阅读”，游标位于采集开始后的 485 秒。此时磁盘读取约 9.2MB/s，平均读请求耗时约 12.7ms，GPU 利用率采样为 0%**，引擎有 **1 个 D 状态线程；这个请求在约 496.49 秒才开始输出正文。

这段 4K 记录呈现了一个首字前的等待现场：磁盘持续读取，线程处于 D 状态，GPU 在该采样点空闲。前面的 16K 请求另采到了文件页等待栈，两段记录都把排查方向指向存储访问。进一步定位 PLE 的耗时，可以在取行和读表处记录时间，再与同一请求的缺页和资源曲线对齐。

这轮实际用起来怎样

短中文对话的首字等待约 7–16 秒，完整回答约 17–46 秒；第三轮的数据纠正保留到了第四轮 JSON。完整 SVG 生成约 70 秒。两次同会话修改各花了约 31 秒，返回原样代码；把原代码和坐标要求放进新会话，约 46 秒得到修改结果。

等待最集中的是本轮第一个长输入：约 4K 词表的首字用了 252.73 秒，整个请求用了 267.79 秒，首字之后约 15 秒生成完设定的 64 个正文 token。对使用者来说，这段时间主要是在等待输入处理后的第一段回答。

这台机器已经可以用来做本地任务实验。下一步计划换成自己的代码和文档，记录完整回答和修改结果，再用同一组任务比较思考模式、内存配置和候选显卡。

注意

  1. 环境。 本轮运行在 Linux 虚拟机，CPU 配置为来宾看到的 16 vCPU。块设备统计来自来宾 vda；物理存储后端和宿主机调度情况未采集。来宾没有 swap。RTX 3090 的架构为 SM 8.6，编译产物包含 sm_86。
  2. 版本与安装。 Strata 源码固定在 7695859aa13afb248bdb4d36f9b2e95707db079d。GGUF 与 ModelScope 提供的 SHA-256 一致，下载文件未固定到不可变 revision。本机遇到 Fabric Manager 的 APT 依赖冲突和系统 CMake 3.22.1 版本偏低，最终使用项目内的 virtualenv 和 CMake 构建，保留全局 NVIDIA 包和驱动。
  3. 请求和计时。 中文、鹈鹕及控制请求共 9 个，每个案例各测一次，结束原因为 stop。这些请求使用标准引擎、prefill 256、thinking none、temperature 0、parallel 1，保留 MTP 和自适应专家策略。客户端在服务端通过 loopback 请求，从请求发出计到首段正文及请求结束；模型加载、截图渲染和事后指标读取另记。
  4. 长输入复测。 输入为 20 个英文词构成的合成词表，正文上限 64 token，三次均以 length 结束，watchdog 沿用默认配置。第二次约 4K 与第一次主体重叠，两次 KV 复用均为 0，系统页缓存保留。默认 benchmark、分块复测和带观测运行各自保留配置与结果。
  5. 任务结果。 中文排障数据是预设题目。鹈鹕修改用文字反馈和 SVG 代码，视觉功能关闭；新会话同时改变了历史和提示布局。更高精度模型、思考模式和并发的对照留给后续测试。
  6. 观测范围。 路由事件记录主模型 MMQ prefill 和验证窗口中的主机计划，验证窗口含被拒绝的推测候选。MTP 草稿与旧的单 token 路径未覆盖，CUDA kernel 起止时间未采集。缓存映射变化含槽位借用、归还和自适应替换；资源采样缺口留空。观测数据来自独立的三个请求。
  7. 作者速度表。 固定版本 README 中，RTX 5070 的 IQ2_XS 数据对应 Ryzen 5 7600、64GB RAM 和引擎 0.1.26；本文使用 RTX 3090、32GB 内存虚拟机和引擎 0.1.43。作者测试条件
