3090 跑 Qwen 写代码：内存加到 64GiB 之后，时间花在哪里

上一篇在 3090 上调整 Strata，把 prefill 分块增大到 2048 后，4K 输入的首 token 延迟降到了约 3.4 秒。不过，让模型根据报错修代码时，仍然要等二三十秒。请求期间，进程会从磁盘读取两百多 MB 数据，decode 吞吐约为 30 token/s。

这台机器当时只有 32GiB 内存。Strata 已经把一部分专家权重放进显存，剩下的主机数据是否也能常驻？内存扩到 64GiB 后，等待会缩短多少？接到编码工具上，它又能完成哪些工作？

本文继续使用同一张 RTX 3090 和 Qwen3.8-Flash-Next-GSQ-RCO IQ2_XS。把 PLE 表常驻内存后，修复请求的平均 decode 吞吐从约 30 提高到 111 token/s，请求期读盘降为零。随后固定配置跑公开编码题：HumanEval+ 通过 156/164，函数生成中位数 3.17 秒；Aider Polyglot 的文件编辑与一次反馈修复通过 112/225，任务耗时中位数 47.5 秒。

这两组编码任务的差别，正好说明了后半篇要观察什么：模型写一个函数需要多久，接上编辑、编译和报错修复后，时间又花在哪里。

64GiB 内存里，实际要放多少数据

先把内存里的数据算清楚。这套模型除了 GPU 上的权重，还要在主机侧访问两块较大的数据。

一块是显存外的专家权重，本次约 16.17GiB。GPU 的 18GiB 专家缓存保存 13432 个专家槽，其他专家权重放在主机锁页内存中，供 CPU 计算或经 PCIe 交给 GPU。

另一块是 PLE 查找表。引擎根据当前及前面的 token 组合计算行号，读取表中的记录，参与后续模型计算。当前模型的表有 320001536 行，每行 90 字节，合计 26.82GiB。mmap 模式按访问需求把文件页带进内存；--ple-io ram 在加载时触碰全表，再用 mlock 保持驻留。PLE 实现

两块主机数据合计约 43GiB。这台虚拟机系统可见内存为 63.3GiB，RAM 模式加载完成后，MemAvailable 约 16.2GiB，用于系统、其他运行数据和请求工作区。本轮单请求、32K 上下文在这个预算内完成测试。

本文用加载日志核对两块数据的大小，再查看系统的 Mlocked 和 MemAvailable：前者确认 PLE 锁页量，后者观察加载后还剩多少可用内存。GPU 的 18GiB 专家缓存单独计量，其他显存用于模型其余计算、KV、MTP 和工作缓冲。

内存已经扩容，为什么还在读盘

容量对照保留同一张 3090、16 vCPU、模型与引擎，依次测试 32GiB mmap、64GiB mmap 和 64GiB RAM。每组两次独立启动，每次两轮任务，下面每项为四次请求的均值。TTFT 记录请求发出到首 token 的等待，decode 吞吐记录输出阶段的生成速度，E2E 记录请求开始到结束的完整耗时。

修复题是生成 retry_delays(attempts, base, cap)：第 i 项为 min(cap, base × 2^i)，同时处理非法参数、零值和 10000 次尝试。首答在大次数测试中出现溢出，再把实际报错交回模型修复。该轮输出上限为 1024 token，CPU/PCIe 使用自动分工。

扩到 64GiB 后继续用 mmap，修复请求仍平均读取约 209MB。新增内存给文件缓存提供了空间，第一次访问尚未缓存的 PLE 页时，仍需从存储读取。切换 RAM 模式后，整张表在模型加载时预读，请求直接访问驻留页。

观测方法是分别记录请求前后的进程读盘字节和 major fault 计数。后者记录需要 I/O 才能处理的缺页。三组各 36 个请求累计读盘分别为 1494.47MB、1253.20MB、0MB，major fault 累计为 12451、10418、0。切到 RAM 模式后，这两项等待来源在请求期间消失，修复生成的平均 decode 吞吐提高到 110.7 token/s；长输入提取的 TTFT 则变化较小。

RAM 组四份修复中，三份写满 1024 token 后被截断，一份完整通过。平均 9.45 秒包含这些截断回答。下一步把输出预算提高到 2048，同时固定 CPU/PCIe 分工，观察生成能否写完，以及哪些资源仍在影响等待。三组容量实验中的自动分工取值保留在文末。

主动常驻还把读取成本移到了启动阶段。两次 RAM 模式的 PLE 装载分别用了 84.1 秒和 2.6 秒，完整加载分别为 226.3 秒和 142.2 秒，操作系统文件缓存状态不同。服务保持运行，可以把这次装载摊到后续请求中。

数据常驻以后，CPU 和 GPU 怎样分工

专家权重在主机内存中时，有两种处理方式：CPU 直接计算，再把结果交给 GPU；或者把权重经 PCIe 搬到 GPU 上计算。pcie_frac 控制未命中显存的专家如何分配。设为 1 时，尽量走 GPU 路径；设为 0.5 时，CPU 专家池承担一部分计算。

为了观察实际取舍，分别用 0.5 和 1 做三次独立启动。每次从同一份专家热度记录开始，按相同顺序执行区间合并、JSONL 日志汇总，以及两份退避修复。修复 A、B 分别使用预先保存的对话和报错，每组重放相同内容。共 48 个请求，输出上限统一为 2048；前缀复用、请求期读盘和 major fault 全部为零。

每行来自三次启动、每次两轮，共六个请求。区间合并的 12 份输出逐字相同，均为 160 token，全部通过 67 项检查。分工从 0.5 改为 1 后，该任务的 CPU 等效占用中位数从 5.26 核降到 1.70 核；日志汇总从 5.60 核降到 1.00 核。GPU 承担更多专家计算，为主机上的应用与工具执行留出了 CPU。

等待时间还受到缓存和输出长度影响。区间合并首轮的显存命中比例为 74.2%–74.6%，第二轮提高到 90.1%–94.3%。重复后，需要 CPU 或 PCIe 处理的路由减少，两种分工的影响也随之变化。

修复 A 在参数 1 下生成更快，E2E 却更长：输出 token 中位数从约 775 增到 1281。修复 B 的输出中位数则从 981 降到 608。因此，本文同时记录 decode 吞吐、完整等待和通过数；三者分别描述生成速度、使用体验和功能结果。

增加预算后，八份回答都自然结束，通过数仍为四份。失败可以发生在很具体的地方：一份代码在外层 for i in range(attempts) 中又嵌入同样的循环，每轮重复追加整段结果。输入 (5, 0.5, 4) 时，预期五项被重复五遍，返回长度变成 25；10000 次用例触发 MemoryError。完整失败回答与测试

同轮另一份代码在计算每一项时逐步翻倍，达到 cap 就结束这一项的乘法循环，再继续追加后续项。同一输入得到 [0.5, 1, 2, 4, 4]，10000 次用例及其余边界检查也全部通过。完整成功回答 · 测试结果

前节的 48 请求对照统一采用 2048 上限，两种分工各有 12 次修复：0.5 组通过 8/12，1 组通过 10/12，各有两次截断。结合较低的主机 CPU 占用，后续编码测试固定使用 PLE RAM、pcie_frac=1、prefill 2048、尾部跳过关闭。

退避修复已经暴露了两类失败：预算用尽时，代码被截断；自然结束时，代码仍可能有循环和边界错误。接下来用公开题集记录更多任务的通过率和完整等待。

Aider Polyglot：改文件并修复一次，通过了多少题

第二组使用 Aider Polyglot 的全部 225 道任务，覆盖 C++、Go、Java、JavaScript、Python、Rust。Aider 读取说明和可编辑源文件，模型输出完整修改文件，随后编译并运行验收测试。首次测试失败，就把错误反馈给模型，再修复一次。

Aider 的语法检查、编辑格式纠错和对话摘要也会调用模型。因此，“首次测试通过”可能已经经过内部纠错；“一次测试反馈”对应两次验收机会。每题 E2E 从任务开始计到结束，包含生成、摘要、修改应用、编译与测试。本轮单次输出上限为 8192。

完整初轮运行 4 小时 30 分 36 秒，首次通过 43/225，最终通过 111/225。检查日志发现，Aider 把 C++ 的 .h 头文件交给了 C 语法解析器，触发大量额外纠错。修正检查器后，全部 26 道 C++ 重跑一遍，另用 22 分 58 秒，具体过程放在下一节。

磁盘等待消失后，还会卡在哪里

Polyglot 初轮 798 次模型调用期间，引擎累计读盘 96KiB，major fault 为 1；采用修正 C++ 结果后的 620 次调用汇总中，两项均为零。这里测量的是每次调用前后引擎进程的计数差值，范围覆盖模型请求；加载阶段和编译器的文件访问另计。

读盘量降下来以后，下面几道题把剩余等待表现得很清楚。

输出很长，任务仍未通过。 JavaScript scale-generator 两次调用都生成满 8192 token，整题耗时 173.6 秒，最终未通过。第二次调用的 decode 为 107.3 token/s、请求期零读盘，输出中反复解释音名转换。生成速度足够快，重复内容仍会消耗预算和时间。

测试反馈占满上下文。 Go paasio 的并发读写计数出现丢失，随后的大量一致性检查报错生成约 933KiB 日志。Aider 把反馈交回模型时，输入达到 415070 token，引擎按 32K 上限拒绝请求。这道题既有初始实现的并发错误，也有修复阶段的反馈长度问题。

工具执行与历史压缩也需要时间。 初轮单独统计的对话摘要约 45.05 分钟；汇总后的编译测试约 40.69 分钟。完整任务时间包含这些操作，生成吞吐只是其中一个环节。

定位这类等待时，先用 Aider 的逐题记录拆出模型调用、摘要和编译测试，再用引擎日志核对输出长度、结束原因及请求期读盘。重复输出对应生成预算，超长报错对应反馈处理，额外纠错对应工具配置。GPU 计算与 PCIe 搬运的完整时间占比，仍需兼容的采集器补测。

这台 64GiB / 3090 已有一套可继续使用的配置：PLE RAM、prefill 2048、pcie_frac=1、tail skip=0。数据驻留后，请求期读盘接近零；更多专家交给 GPU 计算，也给编译和其他工具留出了 CPU。按本轮结果，个人使用可以从以下任务开始：

工作 本轮依据 使用方式
写一个边界明确的 Python 函数 HumanEval+ 156/164；生成中位数 3.17 s 提供签名、输入输出和边界例子，生成后运行测试
修改已有小文件 Polyglot 最终112/225；E2E中位数47.5 s 提供相关接口，检查修改差异，以验收测试决定是否采用
根据报错修复 一次反馈额外挽回69题 回传最相关的错误与失败用例，修复后执行回归测试
跨文件检索、依赖升级、持续多轮开发 本轮尚未测试 下一步用自己的小仓库任务验证

本轮函数题使用 4096 输出上限，Aider 使用 8192。32K 总上下文预留 8192 输出后，输入预算为 24576 token，系统提示、文件内容、历史和测试反馈共同使用这部分空间。回传报错时，保留相关接口、失败用例和关键错误；完整长日志另存文件，按需读取。

本文会让这台机器先完成一个函数或一处局部修改，运行测试后再决定是否继续修复。遇到重复输出，就收缩任务；遇到大段报错，就整理反馈。内存常驻已经解决了这一轮最明显的 I/O 等待，接下来改善个人编码体验，更值得投入的地方是任务拆分、工具配置和测试反馈。
