3090 解锁后调 Strata：算力、搬运与任务验收

上一篇把 PLE 和显存外专家放进 64GiB 内存后，代码生成已经摆脱了反复读盘的等待。这次继续看一个新问题：3090 解锁浮点 Tensor Core 的指令发射速率后，Strata 跑同一个 Qwen 模型，实际能快多少？

本文的解锁前后对照全部来自同一台新建的 32vCPU / 64GiB 虚拟机。本文把测试分成两层。先保持引擎配置不变，测出硬件解锁的直接收益；随后拆分请求耗时，调整计算路径、prefill 分块和 CPU/PCIe 分工，寻找这台机器上的实用配置。全文使用同一份 IQ2_XS 权重，保留全部选中专家的贡献。

同配置补测显示，大分块prefill的解锁收益约13%～19%，decode尚未观察到稳定提速。继续在解锁状态调框架后，17K抽取TTFT从13.49降到5.95秒，减少55.9%；日常候选18432保留相近等待，并留下约8GiB系统内存。本文把这些已测提升与后续的decode研究问题分别记录。

先把解锁的收益量出来

本轮 3090 使用相同的 350W 功耗上限、580.126.09 驱动和 CUDA 12.8。8192³ 的 FP16 输入、FP32 累加 GEMM 从 76.65 提高到 122.34TFLOPS，增加 59.6%；BF16 从 76.09 提高到 125.12TFLOPS，增加 64.4%。六组不同形状与输入格式的完整输出均逐位一致。

接着让 Strata 按原配置处理六类请求，每种状态启动三次服务、每次跑两轮，共 36 个请求。4392-token 抽取的 TTFT 中位数为 4.187 → 4.079 秒；17352-token 为 13.928 → 13.486 秒，分别减少 2.6% 和 3.2%。两组任务通过数均为 34/36。

这里的 TTFT 从客户端发出请求计到首个可见文字；E2E 计到流式请求完整结束。prefill 和 decode 吞吐来自引擎返回的计时。两份修复题允许输出 2048 token，并保存完整回答和边界测试结果。

修复任务是实现指数退避函数 retry_delays(attempts, base, cap)，检查零值、类型、初始值超过上限，以及 10000 次重试等边界。A、B 分别冻结一份有溢出问题的首答，再提供相同的 OverflowError 反馈，让模型继续修复。每个配置收到的完整对话历史保持一致。

算力提升首先体现于大矩阵乘。Strata 的完整请求还要做专家路由、权重整理、CPU 调度、PCIe 搬运，以及逐 token 的验证和草拟，因此接下来要找的是这些步骤各占多少时间。

本文先单独打开引擎的 prefill 分项计时，再用关闭插桩的请求记录速度。17K 输入的诊断时间线为 13.66 秒：

这些分段按计算流上连续的 CUDA event 计时。GPU 等复制或主机工作时，间隔会记入相应阶段。默认 MMQ 路径里的 dequant 标记包括量化权重的 gather 和格式整理；gate/up 与 down 也包括配套的激活、量化等操作。本文据此定位优化方向。

解锁提升的浮点矩阵吞吐只作用于其中使用相应指令的部分。量化专家、拷贝等待和调度仍然要按原来的步骤完成。计时实现与专家路径

看同一个时间轴，区分读盘和 PCIe 搬运

资源采样与请求时间一起保存：引擎进程读盘与 major fault、GPU 利用率/功耗/时钟/显存每两秒一次，PCIe RX/TX 每秒一次。诊断中 GPU 利用率中位数 96%，显存峰值约 23.54GiB，PCIe RX 峰值约 12.5GB/s。

17K 处理期间，读盘很少，PCIe 接收流量持续活跃。本轮虚拟机负载下运行于 PCIe Gen3 ×16。PLE 与显存外专家驻留 RAM 以后，数据会沿 RAM → PCIe → GPU 继续流动；下一步可优化的是一份权重搬过来以后，能为多少 token 服务。

浮点专家和融合内核都实际试一下

固定 2048 分块，把 STRATA_PREFILL_MMQ=0 设为专家先反量化到 FP16、再进行浮点 GEMM。两轮筛选中，4K TTFT 约 4.30 秒、17K 约 14.18 秒，相比默认的 4.08 和 13.49 秒更长；四份修复输出有三份边界测试失败。本文保留原量化专家路径。

同样测试了 STRATA_PF_FUSED=1，运行日志确认进入融合 int8 专家内核。2048 分块下，4K/17K 的 TTFT 约 4.11/13.54 秒，与默认接近。开关已生效，收益由实际耗时决定。路径选择

增大分块，让一次搬运服务更多 token

decode 再看 CPU 与 PCIe 怎么分

显存外专家有两条处理方式：CPU 在系统内存上计算，或把权重交给 GPU 计算。pcie_frac 决定其中交给 PCIe/GPU 的份额。GPU 浮点算力变化后，两条路径的平衡仍受量化内核、链路和 CPU 速度影响。

在 2048 分块的筛选中，pcie_frac=0.5 的 JSONL 代码 decode 中位数约 92.7 token/s，原配置约 78.9；区间合并约 75.0，对照 57.6。随后把该候选与 8192 分块组合，并测试相邻分担比例，确认完整任务耗时及修复质量。

MTP 窗口也做了 2、4、6、8 的对照。窗口越大，一轮可以尝试验证更多候选 token，同时增加草拟和验证成本。本文记录草稿接受数、输出长度和完整等待，最终按已测任务选取窗口。

把块放到更大，RAM 预算也跟着变化

继续设置 --prefill auto:32768 后，这台机器选中了 32768 的上限。17352-token 请求的批量部分为17351 token，单次诊断实际按17408 token布局，借出5747个专家槽。短输入按自己的长度布局；32768是预算上限。

这项配置同时扩大了RAM中保留的专家副本。较大的prompt工作区覆盖更多GPU专家槽，相应专家需要在RAM里留副本，结束时再填回。实测如下：

调优之后，剩下的时间在哪里

17K 输入的大上限诊断中，计算流时间由13.66降到5.34秒，复制等待由3.927降到0.037秒，权重整理等由2.221降到0.296秒，专家gate/up与down等合计由3.346降到1.480秒。这些数值来自独立诊断，正式TTFT采用关闭插桩的六次中位数。

大块让多次专家遍历合并，复制能够与较长的计算区间重叠。此时计算流结束后，还要把借出的5747槽填回，实测705.8ms；这次客户端TTFT为6.11秒。剩余时间分布在专家计算、hyper-connection、GDN、注意力与回填。后续若继续改引擎，优先观察这些具体阶段。

更快的PCIe可作用于尚在搬运与回填的部分，更大的显存可减少专家出入和借用。它们的收益可以沿用相同请求与时间线验证。本文的调优结果已经显示：选好批量和内存布局，比直接替换成浮点专家路径更有效。

到这里，可以分别记下三笔收益：矩阵算力约提升六成；大分块 prefill 的同配置解锁收益约 13%～19%；前文 17K TTFT 减少 55.9%，来自同一解锁状态下的框架调优。 应用体验上，解锁更有助于缩短长输入等待，持续生成的速度改善仍取决于具体执行路径。分阶段对照与指标定义

Decode 的时间线，把搬运和等待再分细一点

接着完成了 82 个请求与三份 Nsight 时间线，分别记录正常速度、逐节点采样、图级采样和辅助分段。主线程负责推进验证、生成 MTP 草稿和等待交换完成；GPU 内部再执行路由专家、HC 混合、注意力和权重搬运。

在一份生成 512 token 的中文诊断请求中，decode 共 8.13 秒。主线程的验证为 5.69 秒、MTP 草稿 0.38 秒、等待缓存交换线程结束 1.08 秒。验证阶段内部，GPU 搬专家权重的 kernel 合计约 1.20 秒，等待 flag B 的自旋 kernel 约 41ms。这些是嵌套层次，表里的分项与 GPU 活动沿同一时间轴核对。

默认路径在 GPU 上执行搬运 kernel，从映射的主机内存读取专家权重；复制引擎还承担冷热专家交换等 H2D/D2H 流量。源码中的 waitB 分段直到搬运 kernel 结束后才记时间，因此较大的 waitB 区间里也包含搬运。把纯 flag 等待与搬运分开以后，后续研究的重点更明确了。

已有开关也做了对照。DMA 与默认路径按正、反顺序各跑独立启动，合并中位数为代码约 +2.6%、中文约 +2.0%，重复范围有重叠。把交换周期从 4 个窗口放宽到 16 个，代码首轮较慢、第二轮才变快；启用 RAM 常驻模式的交换重叠后，主循环外等待下降，verify 内逐层等待增加，净收益仍只有几个百分点。

重叠组还保留了一次最后内容到流式结束约 1.14 秒的等待。后续四次图级采样未重现这条长尾，另有一次约 94ms，其中 CUDA 同步约 0.29ms。它提示收尾也要计入客户端完成时间，原样本原因继续保留待查。

两份固定负载在正常确认组中的输出内容哈希一致。当前日常服务继续使用原配置，DMA 与交换重叠留作候选。decode 分析、计时分层与原始汇总
